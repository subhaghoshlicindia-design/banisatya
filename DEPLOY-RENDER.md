# Deploy from GitHub to Render

This configuration deploys one Node service with the existing SQLite database on a
persistent disk. A paid service is required. Nothing has been deployed or billed by
adding these files. The exact charges and selected account must be reviewed before
creating the service.

## Prepared configuration

`render.yaml` defines:

| Setting | Value |
| --- | --- |
| Service | artha-distributor-portal |
| Runtime | Node 24.22.1 |
| Plan | Starter (paid) |
| Region | Singapore |
| Instances | One |
| Build | npm test |
| Start | node server.cjs |
| Health check | /api/health |
| Disk | 1 GB at /var/data |
| Database | /var/data/artha/portal.sqlite |
| Bootstrap secret | SETUP_TOKEN generated by Render |
| Automatic deployment | After the branch's CI checks pass |

The app uses Render's `RENDER_EXTERNAL_URL` as its allowed HTTPS origin. You do not
need a custom domain. Set `PORTAL_ORIGIN` to your custom HTTPS origin only if you
choose to use one. A trailing slash is accepted; paths and query strings are not.

## GitHub

1. Create or select a GitHub repository. A private repository is appropriate for
   this business portal's source. Connect it to Render with access limited to this
   repository where possible.
2. Push this folder's source to the repository. Keep the root structure: `package.json`,
   `server.cjs` and `render.yaml` must be at the root. Do not upload `data`, `tmp`,
   `.env`, database files, backups, passwords or real investor report files.
3. Wait for the **Portal tests** GitHub Actions workflow to pass on the branch you
   will deploy. The workflow uses synthetic records.

If this is an empty GitHub repository and you are publishing manually from a local
Git checkout, add its actual URL as `origin` and push the current branch. Do not use
force-push when the repository already contains work; reconcile its contents first.

## Render

1. Sign in to Render and connect the selected GitHub repository.
2. Choose **New → Blueprint**, select the repository and deployment branch, and use
   the root `render.yaml`.
3. Review the displayed paid service/disk charges and the Singapore region before
   confirming. If a different region is required, change the configuration first;
   Render does not support changing an existing service's region in place.
4. Deploy and watch the build and health checks. This build runs the database/API
   tests but does not touch the production disk.
5. Verify the service has the persistent disk and that `DATABASE_PATH` matches the
   path above. A free service with an ephemeral filesystem is unsuitable for this
   database. The disk is mounted at runtime; do not run production database changes
   during the build or pre-deploy phase.
6. Open the actual HTTPS URL shown by Render. `/api/health` should return `{"ok":true}`.
   Without signing in, `/api/state` should return HTTP 401.

## First login

1. In the Render service's Environment settings, reveal the generated `SETUP_TOKEN`.
   Do not paste it into GitHub, a support ticket or this document.
2. Open the service's `/setup.html`. Enter the token and create your distributor
   account using your own email/password. There are no default user accounts.
3. Sign in as the distributor. Use **Settings → Employee access** to create employees.
   Give each employee a unique account and temporary password securely. They must
   change their password before they can read reports.
4. Upload reports and create family groups. On a different device, sign in with
   an employee account at the same HTTPS URL and generate a family PDF.
5. Restart/redeploy the service, then sign in and check that the accounts, reports
   and family groups remain. Do this verification with synthetic records before
   importing operational investor data.

If you already have local imports, use **Settings → Existing browser imports** on
the original browser while signed in to the live portal. Browser storage is scoped
to its original address, so old localhost imports cannot be read by a new online
origin. For those imports, upload the original RTA files to the online service.
Account setup does not migrate a local database automatically.

## Operations

- Keep the service at one instance. This SQLite deployment does not support horizontal
  scaling across separate disks. A future multi-instance deployment needs a shared
  database architecture.
- The persistent disk preserves data but is not an independent off-site backup.
  Use `node manage.cjs backup /var/data/artha-backup.sqlite` from the **running
  service's shell**, then download the consistent backup and store it privately.
  A build shell or one-off job does not have this service's mounted disk.
- Follow the backup/recovery instructions in `SERVER-SETUP.md`. Do not recover a
  running SQLite database by copying only its main file while ignoring its WAL.
- Deployments with persistent disks have a short interruption while Render stops
  the old process and starts the new one. The server drains connections on shutdown.
- If the health check fails, inspect Render logs for the first error: check Node
  version, the allowed HTTPS origin, disk permissions and the database path.
