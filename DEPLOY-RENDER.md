# Free hosting with a persistent database

The app now supports Render Free for the server and Neon Free for PostgreSQL.
`render.yaml` creates only the `banisatya-free` web service; it has no persistent disk
and does not provision Render Postgres. Render's free Postgres expires after 30 days,
so it is not the database used by this configuration.

## 1. Create the free persistent database

1. Sign in at https://console.neon.tech and select the **Free** plan.
2. Create a project named `banisatya`, using a region near the server (Singapore
   if available in your account). Keep scale-to-zero enabled.
3. Open the connection dialog and choose the pooled PostgreSQL connection string.
4. Keep that string private. It contains a database password; never paste it into
   GitHub, browser JavaScript or a chat message.

## 2. Deploy the free server

Open https://render.com/deploy?repo=https%3A%2F%2Fgithub.com%2Fsubhaghoshlicindia-design%2Fbanisatya

Review the Blueprint before confirming:

| Setting | Value |
| --- | --- |
| Service | banisatya-free |
| Runtime | Node 24.22.1 |
| Plan | Free |
| Region | Singapore |
| Build | npm ci && npm test |
| Start | node server.cjs |
| Health | /api/health |
| Disk | None |
| DATABASE_URL | Your private Neon pooled connection string |
| SETUP_TOKEN | Generated by Render |

Render prompts for `DATABASE_URL` on initial Blueprint creation. Put the Neon URL
in that private field. Do not select Starter or add a disk. No paid resource is
required by this Blueprint. If updating an existing service, add `DATABASE_URL` in
its Environment page; `sync: false` only prompts during initial creation.

The new name avoids overwriting an older paid/SQLite service. If you previously
created a paid service, it continues to exist and may continue to incur charges.
Do not delete its disk or downgrade it before migrating and verifying its data.
No existing service or disk is removed automatically.

## 3. Set up accounts

1. Wait for Live and open the actual Render HTTPS URL. Do not use GitHub Pages for login.
2. Open `/api/health`; it should return `{"ok":true}`. This checks the server process;
   periodic health probes deliberately avoid waking the free database.
3. In Render Environment, reveal `SETUP_TOKEN` and use it at `/setup.html` to create
   your distributor account. PostgreSQL tables are created automatically at startup.
4. Sign in, open Settings, and create individual employee accounts with temporary
   passwords. Employees must change their temporary password before reading reports.
5. Upload test reports and save a family group. Sign in from another device and
   download an investor/family PDF. Restart the server and verify the data remains.

The server stores accounts, sessions, imports, groups and audit events in PostgreSQL.
The frontend gets report rows only after login. Employees cannot upload or administer accounts.
Active pages check for changes once per minute and download records only when the
workspace revision changes, reducing the free database's network usage.

## Free-tier limits

- Render Free sleeps after 15 minutes without requests. The next visit has a cold start.
- Neon has free compute, storage and transfer quotas. Check the actual Free limits in
  your account; do not upgrade to a usage-billed plan if you require zero payments.
- Render free usage also has bandwidth/build-hour limits. Review account billing and
  spending controls, especially if a payment method is already attached.
- No plan provides unlimited capacity or a production availability guarantee at zero cost.
- Database persistence survives app sleep/redeploy because Neon is separate from Render.
- Neither a temporary Render free Postgres instance nor an app-local SQLite file is used online.

## Existing data and backups

Do not assume a new database contains previous accounts or reports. If you have a
local SQLite database, use the administrator migration described in SERVER-SETUP.md
before creating new accounts. Otherwise upload the original RTA files after setup.
Keep independent private backups; a free tier is not a long-term backup policy.
