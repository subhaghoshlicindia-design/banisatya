# Shared Artha portal

The app now needs its Node server. Opening `index.html` directly or publishing only
the HTML on GitHub Pages will not provide login or shared data.

## Run on this Windows computer

Run `./Start-Portal.ps1` from PowerShell in this folder. It uses Node 24+ installed
on this computer, including the bundled runtime if the default Node is too old.
Keep that terminal open.

1. Open `http://127.0.0.1:3000/setup.html`.
2. Copy the setup token printed by the server into the form. Create your distributor
   account with your own email and a password of 12–128 characters. There are no
   built-in accounts or default passwords. The setup route closes after this account
   is created.
3. Sign in through Distributor Login. Open **Settings → Employee access** and create
   employee accounts. Share temporary passwords securely. Employees must change
   their temporary password before they can access portfolio data.
4. Upload reports. Employees sign in at the same server URL on their devices. They
   can generate individual/family PDFs but cannot upload, clear reports, manage
   families, or administer accounts. The distributor manages shared family groups.
5. If there are old reports in this browser, use **Settings → Existing browser
   imports** to migrate them explicitly. They are never automatically attached to
   a new account. Original local files/storage remain available after migration.

The database is `data/portal.sqlite`. It contains accounts, password hashes,
revocable sessions, imported datasets, family groups and an audit trail. Both
portals share the same database. Changed data refreshes every 15 seconds while a
page is visible; reload for an immediate refresh. Simultaneous edits reject stale
writes so another device cannot silently overwrite newer data.

## GitHub and internet access

The ready-to-use Render Blueprint and instructions are in `render.yaml` and
`DEPLOY-RENDER.md`. That path uses Render's native Node runtime and a disk at
`/var/data`; the Docker path below is an alternative for other hosts.

GitHub stores this source and runs the supplied server tests. GitHub Pages serves
static files and cannot execute this Node server. Deploy the **whole app** to a
Node/Docker server with HTTPS and a persistent disk; do not deploy just the HTML.
No live hosting account, domain or GitHub repository has been configured here.

The included `Dockerfile` builds a single server image without npm dependencies.
Configure your host to run one instance and attach persistent storage at `/app/data`.
Set environment variables using `.env.example` as the reference:

- `NODE_ENV=production`
- `HOST=0.0.0.0`
- `PORT` as required by the host (default 3000)
- `PORTAL_ORIGIN=https://your-actual-server-domain` with no trailing slash
- `DATABASE_PATH=/app/data/portal.sqlite`
- Optionally `SETUP_TOKEN`, generated by your host's secret manager

The host/reverse proxy must terminate HTTPS and forward requests to the Node
service. Production refuses to start without an HTTPS origin and sets Secure,
HttpOnly, SameSite session cookies. The setup token is printed to the server console
if not supplied. Run the initial setup over your HTTPS URL, then use that same URL
from distributor and employee devices. Do not point the frontend at a separate
GitHub Pages origin; this installation uses same-origin cookies and CSRF checks.

Do not use an ephemeral filesystem: losing the database disk loses the business
data. SQLite here supports a single server deployment; multiple server replicas
need a shared managed database architecture. Apply your hosting provider's disk
access controls and encryption, and restrict access to backups.

## Backups and password recovery

Use Node 24+ in the following commands (the Windows launcher can locate that binary).
Create a consistent SQLite backup, including data still in the WAL:

```powershell
node manage.cjs backup 'E:\PrivateBackups\artha-2026-11-07.sqlite'
```

Keep backups outside GitHub and test restoration. To restore, stop the server,
preserve the current database and its `-wal`/`-shm` files, then restore a consistent
backup as `DATABASE_PATH` before restarting. Do not simply copy an open main SQLite
file while ignoring its WAL.

Distributors can reset/disable employees in Settings. A reset revokes existing
sessions and requires a password change on the next login. For lost distributor
access, a server administrator can use the offline recovery command. This requires
access to the server filesystem/environment; it is not an unauthenticated web route.

```powershell
$portalRecovery = Read-Host 'New temporary distributor password' -AsSecureString
$env:NEW_PASSWORD = [System.Net.NetworkCredential]::new('', $portalRecovery).Password
node manage.cjs reset-distributor 'your-email@example.com'
Remove-Item Env:NEW_PASSWORD
```

Users can change their password from Settings or the employee account menu.
Password changes revoke sessions on other devices. Self-service email resets and
outbound email are not configured.

## Tests

`npm test` runs database/API tests with synthetic records, including permissions,
CSRF, conflicting edits, duplicate handling, persistent data after restart and
session revocation. `.github/workflows/test.yml` runs these on GitHub.

`node test-browser.cjs` additionally requires Playwright and a browser. Set
`PLAYWRIGHT_MODULE_PATH` and `BROWSER_EXECUTABLE` if they are not installed in the
usual locations. It checks the complete workflow in independent browser contexts:
first setup, logins, account creation, mandatory password change, all five import
categories, automatic shared family updates, PDF download and employee disabling.

Reports still reflect imported data. Customized real RTA files should be validated
before operational use; this implementation does not add capital-gains/tax rules.
